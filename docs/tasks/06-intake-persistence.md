## Decisions

- **T06-D01 — 2026-09-30:** `Intake::Models::SellerItem` maps to `intake_seller_items`, one row per exact `(seller_name, seller_product_id)`, protected by a unique index. `active_source_input` retains exact supplied values and `active_source_comparison` retains the T04 normalized name/brand/category tuple. `resolution` is `pending`, `linked`, `created`, `declined`, or `displaced`; `product_id` is the current Catalog reference. Pending may have a product because changed source must leave an old association untouched. Linked/created require a product; declined/displaced require no product. An unchanged declined or displaced key therefore remains addressable without an association.
- **T06-D02 — 2026-09-30:** `intake_review_cases` stores one source-version snapshot per case (`source_input`, `source_comparison`, opening batch/position), status `pending`, `resolved`, or `superseded`, reason, current `evidence_revision`, and conflicting-association snapshot. A partial unique index on `seller_item_id` for pending/resolved cases ensures at most one active version. A changed source is installed by superseding the old active case and inserting a new pending case in one transaction. `attr_readonly` protects the case's opening source snapshot through Active Record.
- **T06-D03 — 2026-09-30:** `intake_batches` records source name and expected element count. `intake_row_results` has unique `(batch_id, source_position)` with one-based positions, JSON text of each parsed input element (including the literal `null`), nullable exact seller key, outcome `linked`, `created`, `already_imported`, `pending_review`, or `failed`, reason, validation errors, and nullable product/case IDs. Failed rows need no valid key. A pending-review row requires a case. The row result is Active Record read-only after insert, so later case transitions do not alter import-time outcomes. T07 must insert exactly `input_count` rows; a database constraint cannot require full position coverage across rows.
- **T06-D04 — 2026-09-30:** `intake_review_candidates` stores ranked, versioned evidence with product ID, score, original/normalized values, differing fields, and a conflicting-association snapshot. Unique `(case, revision, rank)` and `(case, revision, product)` prevent duplicate evidence positions. `intake_review_rejections` stores one reviewer/time/reason per candidate snapshot, so rejection remains attached when evidence revisions advance. `intake_review_corrections` stores full corrected input and comparison snapshots, reviewer, and time separately from source values. Evidence, rejections, and corrections are Active Record read-only once inserted; rematches append new evidence revisions.
- **T06-D05 — 2026-09-30:** `intake_review_decisions` stores one final decision per case, with reviewer, time, result (`linked`, `created`, or `kept_existing`), resulting product, optional reason, and optional displaced/declined `intake_seller_items` IDs. A kept-existing decision requires a declined key; every decision requires a resulting product. Decisions are Active Record read-only after insertion and historical foreign keys restrict referenced record deletion. The application must use normal model writes; direct SQL update/delete bypasses the Active Record read-only guard. No PostgreSQL trigger is included because this application uses `schema.rb` for fresh database loads.
- **T06-D06 — 2026-09-30:** Intake stores Catalog `product_id` references with PostgreSQL foreign keys and read-only ID lookups, without Catalog model associations or Catalog-to-Intake dependencies. Catalog writes remain exclusively through `Catalog::Public`. The database provides check constraints for states, positions, score range, JSON syntax, required text, key pair completeness, and resolution/product compatibility; model validators provide earlier feedback where practical.

## Handoff

T07–T08 should create one `Batch` per parsed JSON array with `input_count` set to the array length and one immutable `RowResult` per one-based element position, including failures. Serialize each element with JSON to `input_json`; use `validation_errors` from T04 for invalid rows. Count outcomes from `batch.row_results.group(:outcome).count`, and check the row count equals `input_count` before declaring the batch complete. For valid keys, use `SellerItem.find_exact(seller_name:, seller_product_id:)`; compare incoming T04 identity with `active_source_comparison`, never corrected data. An unchanged pending key points another row result to `seller_item.active_case`; an unchanged linked/created/declined/displaced key yields `already_imported` with the retained product or decision reason. For changed source, lock the seller item, supersede the old active case, update `active_source_input` and `active_source_comparison`, set `resolution: "pending"` while retaining any current `product_id`, and insert a new case atomically. The unique key and partial active-case indexes handle concurrent races.

T09–T11 should query the review queue through `ReviewCase.where(status: "pending")`, filter by `batch_id` or `seller_item.seller_name`, and order by ID. Display the case's immutable `source_input`, latest correction (if any) ordered by `corrected_at, id`, and `review_candidates.where(evidence_revision: review_case.evidence_revision).order(:rank)`. Candidate records are snapshots of the T05 evidence contract. On rematch, increment `evidence_revision` and insert fresh candidates; use all prior `ReviewRejection` records for the case to keep products rejected across revisions. Corrections and rejections append rows; they never alter source identity or auto-resolve the case. Conflict evidence is available in both case-level and candidate-level `conflicting_association` JSON.

T10–T13 final decisions should lock the active seller item/case, recheck current Catalog and candidate evidence, perform Catalog writes only through `Catalog::Public`, then insert one `ReviewDecision`, mark the case resolved, and update seller-item resolution/product in the same database transaction. A `kept_existing` decision carries the surviving `product_id` and `declined_seller_item_id`; the declined seller item has `resolution: "declined"`, `product_id: nil`, and its unchanged `active_source_comparison`. Replacing an ID records `displaced_seller_item_id` and leaves that old seller item with `resolution: "displaced"`, `product_id: nil`, and its original active source identity. These keys remain queryable by exact key for future `already_imported` outcomes. Prior cases and decisions remain addressable through `seller_item.review_cases` even after a newer version supersedes them. Product references are database foreign keys for history, but no Intake code writes Catalog models directly. T06 establishes persistence, not importer or reviewer commands.
